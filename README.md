# dns-monitor

DoH and DoT health checks for the Bancuh DNS resolvers, reporting to
[uptime-kuma](https://github.com/louislam/uptime-kuma) push monitors.

Deployed as a Deployment from `flux-deploy`
(`clusters/vmbr1-k3s/services/dns-monitor/`).

## Why this exists

Uptime Kuma's built-in `HTTP(s)` monitor cannot check DoH against a current
dnsdist. dnsdist 1.9+ enforces RFC 8484 section 5.2 and rejects DoH over
HTTP/1.1 with a `400`; Uptime Kuma's HTTP monitor uses axios, which is
HTTP/1.1 only. There is also no built-in monitor type that speaks real DoT.

So this speaks both itself, and asserts more than a 2xx status:

- **DoH** — an RFC 8484 `POST` of a wire-format query, which must come back
  over **HTTP/2** (negotiated by ALPN, not forced) with `NOERROR`.
- **DoT** — a TLS connection to `:853` carrying a length-prefixed query, which
  must come back `NOERROR`.
- **cert** — the leaf certificate from the `:443` handshake, alerting on days
  remaining rather than only on an outright failure.

All three verify the server certificate against the platform trust store, so a
stale or expired certificate is caught rather than silently accepted. The DoH,
DoT and certificate checks share one verifier, so they cannot disagree about
whether a chain is valid.

## How it runs

One long-lived process. Every `INTERVAL` it checks every node, and every check
of every node runs as its own task: a round takes as long as its slowest single
check, not the sum of all of them.

That bound is the reason for the design. Checked serially, seven nodes timing
out at 8s each is well over two minutes, so an outage in one region delays —
and past a deadline, starves — the checks for every region after it in the
list, and healthy nodes alarm because nothing reported them. Concurrently, a
fully unreachable fleet still finishes a round in about the per-check timeout.

Certificates are read from the handshake the check already performs, and each
node's address is resolved once per round so all three of its checks address
the same server.

A failed check is repeated once, after a short pause, before it is reported
down. A single bad probe used to be enough to notify, and in practice most were
transient: three alerts on 4 September were each one failed check that passed
again on the next round. Confirming costs one extra probe on the rare failing
check, and a real outage is still reported within the round it started in. A
certificate near expiry is reported the first time, since asking again cannot
change the answer.

A failed push is logged and left for the next round rather than failing the
process: uptime-kuma's heartbeat window is wider than one interval, so a single
miss is absorbed.

`/healthz` on `HEALTH_PORT` reports how long ago the last round finished and
fails once that exceeds three intervals. The Deployment uses it as a liveness
probe — a long-lived process does not get the free restart that a CronJob tick
gave, so a wedged loop needs to be caught rather than discovered when every
monitor alarms at once.

## Configuration

All via environment variables.

| var | default | meaning |
|---|---|---|
| `NODES` | *(required)* | space-separated short names, e.g. `jp-dns2 jp-dns1` |
| `DOMAIN` | `bancuh.com` | suffix appended to each short name |
| `KUMA` | in-cluster uptime-kuma service | base URL for push |
| `QNAME` | `careers.opendns.com` | name to resolve |
| `TIMEOUT` | `8` | per-check timeout, seconds |
| `WARN_DAYS` | `21` | report a certificate down below this many days left |
| `INTERVAL` | `120` | seconds between rounds |
| `HEALTH_PORT` | `8080` | port for `/healthz` |
| `TOKEN_<NODE>_DOH` | — | push token, e.g. `TOKEN_JP_DNS2_DOH` |
| `TOKEN_<NODE>_DOT` | — | push token, e.g. `TOKEN_JP_DNS2_DOT` |
| `TOKEN_<NODE>_CERT` | — | push token, e.g. `TOKEN_JP_DNS2_CERT` |

`<NODE>` is the short name uppercased with `-` replaced by `_`.

Adding a node is a config change only — no image rebuild.

Push tokens are generated by uptime-kuma when a Push monitor is created and
**cannot be chosen**: the Push URL field in the UI accepts typed text but does
not bind to the stored token. Read each token from its monitor's edit page.

`WARN_DAYS` defaults to 21 because Let's Encrypt certificates are 90 days and
renewal begins at 30 days remaining, so anything under ~21 means a renewal that
should already have happened has not. Days remaining is pushed as the ping
value so uptime-kuma graphs it: a healthy fleet shows a sawtooth resetting at
each renewal, and a line trending to zero means renewal has stopped working,
visible weeks before it becomes an outage.

## Run locally

```sh
docker run --rm \
  -e KUMA=https://uptime-kuma.example.net \
  -e NODES="jp-dns2" \
  -e TOKEN_JP_DNS2_DOH=xxxx -e TOKEN_JP_DNS2_DOT=yyyy -e TOKEN_JP_DNS2_CERT=zzzz \
  ghcr.io/ragibkl/dns-monitor:latest
```

Output is one line per check, plus the round time:

```
INFO dns_monitor: UP jp-dns2.bancuh.com doh ok ping=387.8
INFO dns_monitor: UP jp-dns2.bancuh.com dot ok ping=521.4
INFO dns_monitor: UP jp-dns2.bancuh.com cert ok, 88 days ping=88
INFO dns_monitor: round finished in 1.140240252s
```

A failed check is reported to uptime-kuma as `down` and logged at `warn`.
